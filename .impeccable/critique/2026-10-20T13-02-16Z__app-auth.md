## Design Specificity Verdict

**LLM assessment:** Visually, both pages are unmistakably CodeInQuest — pixel chest icon, Pixelify Sans heading, 3px borders, single hard shadow, gold-only accent, applied identically and correctly on both files (no drift). But the copy is interchangeable with any generic SaaS auth screen and never once references the division ladder — the exact thing the landing page just sold the visitor on seconds earlier. It's a costume without the character underneath: PRODUCT.md's own principle states competition is "le moteur de rétention, pas un habillage," yet that hook disappears completely the moment a visitor leaves the landing page.

**Deterministic scan:** `impeccable detect --json app/auth` ran clean — zero findings, confirmed as a genuine clean result (the detector's `--help` output was checked to rule out a silent failure).

**Visual overlays:** Blocked by the same site-wide CSP confirmed on every prior page in this app — not a regression.

**Validation cross-check (source-verified):** `lib/quiz/validations.ts`'s `signupSchema` has FOUR separate password rules (`.min(8)`, three `.regex()` checks for uppercase/lowercase/digit), each producing its own Zod issue on failure. `signup/page.tsx`'s `validateForm` (lines 44-50) does `newErrors[issue.path[0].toString()] = issue.message` inside a `forEach` over all issues — confirmed in source: since all four rules share the same field path (`password`), each new issue silently overwrites the previous one, so a password failing multiple rules at once only ever surfaces the last failure checked.

## Overall Impression

The system-level craft holds up perfectly (zero visual drift between signin/signup, correct tokens throughout), but this is the one screen in the whole funnel where the product's actual differentiator goes completely silent, and it ships a real, verified logic bug: the signup form's validation can only ever show a user one password problem at a time even when several exist simultaneously, and the one moment this funnel should feel like a win — a successful signup — gets zero acknowledgment.

## Priority Issues

**[P1] Password validation errors overwrite each other instead of accumulating**
- **Why it matters:** Confirmed by reading both the Zod schema and the form code together — a password like "weak" fails three rules at once (min-length, uppercase, digit), but `signup/page.tsx`'s error-collection loop only ever retains the last one. A user fixes the shown issue, resubmits, and is told about a *new* problem that existed all along — a frustrating trial-and-error loop at the exact step where PRODUCT.md's target users (self-taught beginners) are most likely to churn.
- **Fix:** Accumulate messages per field (join with `; ` or render a bullet list) instead of overwriting; better, show all password rules as a static checklist under the field that live-updates as the user types.
- **Suggested command:** `/impeccable harden`

**[P1] Successful signup gives zero confirmation**
- **Why it matters:** Confirmed in source — `signup/page.tsx` redirects to `/auth/signin?registered=true`, but `signin/page.tsx` never reads `registered` from `searchParams` anywhere. The one positive moment in this entire funnel disappears silently; a first-timer has no idea whether their account was actually created.
- **Fix:** Read the param on signin and render a success banner (reusing the existing error-banner markup, in `victory-green-surface`), e.g. "Compte créé ! Connectez-vous pour rejoindre la Division Bronze."
- **Suggested command:** `/impeccable delight`

**[P2] No `autocomplete` attributes on any input**
- **Why it matters:** Confirmed via grep and live DOM inspection — zero `autoComplete`/`autocomplete` anywhere across both files' 6 inputs. Breaks password-manager autofill and "save password" prompts for every user on both forms.
- **Fix:** Add `autoComplete="email"` to both email inputs, `autoComplete="current-password"` to signin's password field, `autoComplete="new-password"` to signup's password + confirm fields, `autoComplete="name"` to the name field.
- **Suggested command:** `/impeccable harden`

**[P2] Submit button has no focus ring, breaking the system's own documented rule**
- **Why it matters:** Confirmed in source — both buttons' className strings contain no `focus:ring` class at all, while every adjacent input correctly carries `focus:outline-none focus:ring-[3px] focus:ring-focus-ring`. DESIGN.md explicitly specifies this treatment for buttons; the gap is jarring precisely because it's inconsistent with the inputs one tab-stop away.
- **Fix:** Add `focus:outline-none focus:ring-[3px] focus:ring-focus-ring` to the button className in both files.
- **Suggested command:** `/impeccable harden`

**[P3] No password visibility toggle**
- **Why it matters:** Both password fields (and confirm-password) are permanently masked with no eye-icon toggle. Combined with no live match-checking, verifying a typed password requires trusting two masked fields matched — avoidable friction right at signup.
- **Fix:** Add a `PixelIcon` eye/eye-off toggle inside each password field.
- **Suggested command:** `/impeccable polish`

No P0 — nothing breaks a hard DESIGN.md invariant, and no security-relevant information leaks (signin's error message correctly stays generic).

## What's Working

- **Signin's error banner**: specific, non-blaming, retains the typed email on failure, and deliberately doesn't distinguish "wrong email" from "wrong password" — a good security/UX tradeoff.
- **System-token compliance**: 3px borders, hard shadow, zero radius, gold-only accent, uppercase labels applied identically and correctly across both pages — confirmed by diffing the source, zero drift.
- **Signup's duplicate-email handling**: returns a specific, actionable "Un utilisateur avec cet email existe déjà" rather than a generic failure.

## Persona Red Flags

**Jordan (First-Timer):** Hits the password overwrite bug on a first attempt, fixing one rule at a time across repeated submits — exactly the kind of confusing trial-and-error a non-technical beginner is least equipped to debug alone. After finally succeeding, lands on a bare signin form with no "it worked" signal and no mention of Bronze division.

**Sam (Accessibility-Dependent User):** Tabbing to either page's primary CTA produces the browser's default outline instead of the documented gold ring — jarring right after the inputs show the correct treatment. Zero `autocomplete` attributes mean password managers many users rely on won't reliably offer to fill or save credentials.

**Riley (Stress-Tester):** Signin's wrong-password path is clean and correctly scoped. Signup's weak-password path surfaces the whack-a-mole validation bug within two submits — reads as a functional defect, not a deliberate constraint.

## Minor Observations

- Both pages fully duplicate the card/input/button markup rather than sharing a component — no drift today, but the identical missing-focus-ring gap on both files is itself a sign style changes already have to be manually kept in sync.
- Loading state replaces the button's icon with plain text ("Connexion…"/"Inscription…") rather than keeping an icon/spinner.
- The CGU/politique de confidentialité consent is a passive footnote link rather than an explicit checkbox — defensible for an MVP, worth a conscious call given dedicated CGU/RGPD pages already exist.
- Contrast checked and solid everywhere: secondary/placeholder text ≈5.2-5.6:1, error text ≈5.0:1, primary text ≈13.7:1, button text ≈10.9:1.
